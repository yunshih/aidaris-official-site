The Code Is Fine. Nobody Understands the System.

🌐 中文

October 2026 · 7 min read · Aidaris Technologies Engineering Philosophy

System Legibility AI & Work Engineering Governance Code Quality Architecture

Earlier this year, Anthropic published a study on how work has changed inside the company. The numbers are specific: code commits per engineer rose approximately fivefold over six months. Code written by agents showed no higher rate of later removal or reversion than code written by humans.

The conclusion is cautiously optimistic: AI increased output, and quality did not noticeably decline.

This should be good news. The problem is that "not reverted" and "someone understands this system" are two entirely different things.

Quality Floor and System Understanding Are Not the Same Thing

The traditional code quality signals — tests passing, no obvious bugs, review checklist satisfied — AI hits them reliably. This is not high praise; it is an accurate description of how LLMs work. They perform consistently on known patterns, consistently enough to keep quality metrics stable.

So the quality floor has risen, or at least held.

But the quality floor measures one question: "Does this code run, and does it run without obvious problems?" It has never measured a different question: six months from now, can an engineer who wasn't involved read this system, understand it, and make changes without breaking it?

That capability has a name: system legibility.

What System Legibility Is

In a high-legibility system, an engineer with no prior context can:

  • Identify the system's boundaries and areas of responsibility
  • Trace the likely scope of any given change
  • Distinguish intentional design decisions from historical accidents
  • Read architectural intent, not just architectural outcome

Legibility is not maintained through documentation. Documentation always lags implementation, and the moments when legibility matters most are usually the moments when documentation is least complete. Legibility is maintained through structural consistency, naming precision, and design intent distributed across the codebase — things that exist, but don't appear in any CI metric.

AI is neutral on this. It does not actively degrade legibility, but it does not care about legibility either. Every locally correct decision it makes does not necessarily add up to a globally comprehensible system. When five different agent sessions, initiated by five different people, each solve a local problem, and nobody is asking what the system looks like when all five are combined — legibility quietly erodes.

Attention Is the Real Bottleneck

There is another number in the Anthropic study worth noting: 80% of interactive agent session time is spent waiting for human input.

The implication is that human attention is already the bottleneck for the entire system.

When an engineer goes from reviewing five pull requests a day to twenty-five, the nature of review changes. Not "I have read and understood this code and confirmed it fits the overall design intent," but "this looks fine, tests passed, approved." Both count as an approval. Only the first maintains legibility.

This is not laziness. It is the rational response to a structural constraint on human attention. Five times the output does not produce five times the depth of comprehension. With attention fixed, review density thins, and the depth of understanding each PR receives is shallower than before.

The code went through. The understanding did not follow.

The Pressure Test That Disappeared

The sharp decline in junior engineers is one symptom of this trend. Anthropic's data shows the junior share of technical hires falling from 27% to 9%.

What matters here is not the employment number — it is the role junior engineers played in the organization. They were the ones who had to read the system from scratch, and who were therefore forced to ask "why does this work this way?" These questions are inconvenient. They are also the natural pressure test for whether a system is actually understandable.

When that layer disappears, so do the questions — not because the system became easier to understand, but because nobody is forced to understand it anymore.

The Governance Gap

Quality metrics have corresponding governance mechanisms: CI/CD, test coverage, static analysis, vulnerability scanning. These tools exist, they are increasingly automated, and they work just as well in AI-assisted development environments.

System legibility has no equivalent governance mechanism.

There is no metric measuring "how easy is this system for the next engineer to understand." There is no gate asking "does this pull request make the system's intent clearer or more opaque." Architecture review typically triggers only for large new features, not across the daily volume of AI-assisted commits.

The result: the quality floor looks stable, while the system's overall legibility erodes without notice. Not a single collapse — a silent accumulation of every "good enough, merge it."

This is not a technical problem. Nothing is technically wrong. It is a governance problem: who is responsible for regularly asking "does anyone still understand this system," and ensuring that the answer matters.

AI has made code production abundant. The next scarce thing is system-level judgment — knowing what a system is, why it is built the way it is, and where it can go next. Preserving that capability is the work AIDARIS helps engineering organizations do.
